# TanStack AI: the APIs that matter

**Versions:** `@tanstack/ai` 0.43.1 · `@tanstack/ai-react` 0.19.1 ·
`@tanstack/ai-persistence` 0.1.1 · `@tanstack/ai-openrouter` 0.15.11

`@tanstack/ai`'s index re-exports well over two hundred symbols — activities,
realtime, MCP, tools, middleware, interrupts, sandbox capabilities, media
generation. A durable chat needs about a dozen. This is the map: what the dozen
are, what each one owns, and where the rest sits so you can recognise it later.

## Summary

```ts
// ── server ────────────────────────────────────────────────────────────────
createOpenRouterText(model, apiKey, opts)      // the adapter. one per app.
chatParamsFromRequestBody(body)                // AG-UI body → { messages, threadId, runId }
chat({ adapter, messages, threadId, runId, middleware })   // → AsyncIterable<StreamChunk>
toServerSentEventsResponse(stream, { durability: { adapter } })   // POST
resumeServerSentEventsResponse({ adapter })                       // GET resume
resolveResumeRunId(request)                    // X-Run-Id, then ?runId
withPersistence(persistence)                   // chat middleware
defineAIPersistence({ stores })                // your 4 stores → ChatPersistence
reconstructChat(persistence, request)          // GET hydrate → JSON Response

// ── client ────────────────────────────────────────────────────────────────
fetchServerSentEvents('/api/chat')             // the connection
createChatClientOptions({ connection, persistence, threadId })
useChat(options)                               // { messages, sendMessage, stop, isLoading, error }
InferChatMessages<typeof options>              // never hand-type a message
```

Two interfaces you *implement* rather than call: `StreamDurability` (five
methods) and the four persistence stores. Both are covered in detail in
[postgres-integration.md](./postgres-integration.md).

## 1. The adapter — `createOpenRouterText`

```ts
// src/server/ai/adapter.ts
export const textAdapter = createOpenRouterText(
  'qwen/qwen3.6-flash',
  env.OPENROUTER_API_KEY,
  { httpReferer: env.APP_URL, appTitle: 'tanstack-ai-durable-run-poc' },
)
```

**The only place in the codebase that names a model.** Changing providers is this
line and nothing else. Never construct an adapter inside a route handler, and
never inline a model string at a call site — both turn a one-line swap into a
search-and-replace.

**Gotcha learned here:** the model string is a typed union, and the package's
catalogue lags the provider. `qwen/qwen3.7-flash` was live on OpenRouter and
absent from `@tanstack/ai-openrouter@0.15.11`'s union. The right move was to pin
the previous point release, not to cast past the type — a cast would have
silently outlived the reason for it.

## 2. Parsing the request — `chatParamsFromRequestBody`

```ts
const { messages, threadId, runId } = await chatParamsFromRequestBody(body)
```

Normalises the AG-UI wire body the client posts into the shape `chat()` wants.
The sibling `chatParamsFromRequest(request)` does the same from a `Request` —
use the body variant when you want to Zod-validate first, which you should:

```ts
const parsedBody = startRunRequestSchema.safeParse(await request.json())
if (!parsedBody.success) return badRequest(z.prettifyError(parsedBody.error))
const { messages, threadId, runId } = await chatParamsFromRequestBody(parsedBody.data)
```

The schema is a **`z.looseObject`**, deliberately. The AG-UI body legitimately
carries fields this app doesn't read — tools, state, forwarded props — and
`z.object`'s stripping would corrupt the payload handed on for normalisation. The
strictness that matters is only the run identity: a body whose `threadId` or
`runId` is missing or empty produces a run that can never be rejoined.

## 3. Running the model — `chat`

```ts
const stream = chat({
  adapter: textAdapter,
  messages,
  threadId,
  runId,
  middleware: [withPersistence(chatPersistence)],
})
```

Returns an async iterable of `StreamChunk`. Everything else — durability,
persistence, tools, agent loops — hangs off this call:

| Option | What it adds |
| :-- | :-- |
| `middleware` | persistence, OTel, structured output, tool hooks |
| `tools` | `toolDefinition(...)` instances, with `.server()` / `.client()` impls |
| `agentLoop` strategies | `maxIterations`, `untilFinishReason`, `combineStrategies` |
| `systemPrompts` | normalised via `normalizeSystemPrompts` |

`threadId` and `runId` are passed *in*, not generated by `chat()`. That matters:
the ids are the client's, and the whole durability story depends on the client
being able to come back and name the run it started.

## 4. The two response helpers

```ts
// POST — run and log
return toServerSentEventsResponse(stream, {
  durability: { adapter: streamStore(request, runId) },
})

// GET — replay the log, no new messages
return resumeServerSentEventsResponse({ adapter: streamStore(request) })
```

These are the durable-run contract. **Both handlers are load-bearing** — a
POST-only endpoint is not durable.

The behaviour worth knowing, because it's the whole trick and it isn't obvious
from the signatures: **a client that drops mid-run does not cancel it.** On a
fresh run core gives the producer and the delivery side *separate* abort
controllers. The browser going away aborts delivery; the producer keeps draining
the model into the durability adapter with nobody listening. That is why a client
rejoining thirty seconds later still gets the whole reply. The route only wires
it.

Same helpers exist for plain HTTP streams — `toHttpResponse`, `resumeHttpResponse`,
`toHttpStream` — if you'd rather not speak SSE. SSE is the better fit here
because `Last-Event-ID` gives you native browser reconnect for free.

### `resolveResumeRunId(request)`

The library's single implementation of the run-id precedence: **`X-Run-Id`
header first, then `?runId`**. Exported, so your durability adapter and the
transport can never disagree about which run a request means.

Its offset counterpart is *not* exported. The precedence is `Last-Event-ID`
header first, then `?offset` — including the truthiness test, so an empty header
falls through. We had to restate it in `src/server/ai/resume-position.ts`, once,
shared by both the endpoint's validation and the backend's run resolution. Two
readings of the same request that disagreed would reject resumes the transport
would have served.

## 5. Durability — `StreamDurability`

The pluggable backend the response helpers write to and read from. Five methods:

| Method | Contract |
| :-- | :-- |
| `resumeFrom()` | the offset captured from the request, or `null` for a producer |
| `append(chunks)` | persist a batch, return **one offset per chunk, in order** |
| `read(offset, signal)` | async-iterate everything **strictly after** `offset` |
| `close()` | terminalise the log; core awaits this on **every** producer exit |
| `snapshot()` | everything stored right now, never a wait, `[]` for an unknown run |

Offsets are **opaque to the transport and owned by the adapter**. They become SSE
`id:` lines, so they must be non-empty, contain no CR/LF, and equal their own
trimmed form.

`memoryStream` is the reference implementation and doubles as the spec — read
`stream-durability.d.ts` next to any backend you write. It is for development
only: its logs live in a process-global map, so it proves *reconnect*, not
*durability*. **Whichever backend is active must be stated plainly in a demo.**

`UpsertableStreamDurability` adds an optional `upsert` for run drivers that
re-derive offsets after a crash. Deliberately a separate interface, not an
optional `append` parameter, so requiring the capability is a compile error
rather than a runtime surprise. We don't implement it — and `streamStore`'s
return type is narrowed to plain `StreamDurability` precisely so no caller can
come to depend on it.

## 6. Persistence — `defineAIPersistence`, `withPersistence`, `reconstructChat`

A separate package (`@tanstack/ai-persistence`) and a genuinely separate layer.

```ts
export const chatPersistence: ChatPersistence = defineAIPersistence({
  stores: { messages, runs, interrupts, metadata },
})
```

Four stores:

| Store | Owns |
| :-- | :-- |
| `messages` | `loadThread` / `saveThread` — the transcript |
| `runs` | `createOrResume`, `update`, `findActiveRun`, `listByThread`, `listReclaimable` |
| `interrupts` | human-in-the-loop approvals: `create`, `resolve`, `cancel`, `list*` |
| `metadata` | app-owned JSON by `(namespace, key)` |

**Type it as `ChatPersistence`, not the inferred type.** `defineAIPersistence`
infers an all-optional bag, and `withPersistence` rejects that — a possibly
undefined message store is not one it can drive.

`withPersistence(persistence)` is the middleware that writes the transcript, the
run lifecycle, and token usage as each turn completes.

`reconstructChat(persistence, request, options?)` is the read side, and it is the
piece that makes a rejoin work anywhere:

```ts
// GET /api/chat?threadId=…  →
{ messages: UIMessage[], activeRun: { runId } | null, interrupts: {…} | null }
```

`activeRun` is resolved server-side from `runs.findActiveRun(threadId)`, so the
client learns *"there is a live run to tail"* without ever having stored a run
id. An unknown thread returns an empty transcript rather than a 404, so the
first load needs no special case.

> ⚠️ **`reconstructChat` enforces no tenancy.** Without an `authorize` callback,
> anyone who guesses a `?threadId=` receives the full transcript. This POC has no
> sessions and says so in a comment; anything with real users must pass one.

## 7. The client — `useChat`

```ts
const durableChatConnection = fetchServerSentEvents('/api/chat')   // module level

export function createChatOptions(threadId: string) {
  return createChatClientOptions({
    connection: durableChatConnection,
    persistence: true,
    threadId,
  })
}

const { messages, sendMessage, stop, isLoading, error } = useChat(createChatOptions(threadId))
```

Three things doing real work:

- **`connection` is read once.** `useChat` keeps the transport it was constructed
  with, so building it per render is pure waste. Module scope.
- **`persistence: true` means server-authoritative.** The browser caches nothing.
  On mount the client issues `GET ?threadId=` itself, paints what comes back, and
  tails `activeRun` if there is one. The alternatives —
  `localStoragePersistence`, `sessionStoragePersistence`, `indexedDBPersistence`
  — make a reload resumable *in that browser only*, which is a weaker claim.
- **`threadId` is both the wire identity and the hydration key.** Same URL → same
  thread → same in-flight run.

**There is no `useEffect` rejoining the run, and there must not be.** `useChat`
hydrates and tails as it constructs its client. A hand-wired stream would be a
second consumer of the same run, racing the one that already exists.

To reset for a different conversation, key the container:
`<Conversation key={threadId} threadId={threadId} />`.

### Types: infer, never hand-write

```ts
export type ConversationMessage = InferChatMessages<ReturnType<typeof createChatOptions>>[number]
export type ConversationMessagePart = ConversationMessage['parts'][number]
```

A message is a **list of parts**, not a string. Reading `parts[0].content` works
right up until the model thinks first, and then renders a blank reply. Switch on
`part.type` — `text`, `thinking`, `tool-call`, `tool-result` — and keep a
`default` branch that degrades to a label, so a part type you've never seen
doesn't take the page down mid-stream.

## 8. What we did not use, and where it lives

Recognising these saves time later:

| Area | Symbols |
| :-- | :-- |
| Tools | `toolDefinition`, `createToolRegistry`, `ToolCallManager`, `needsApproval` + `approvalSchema` |
| Agent loops | `maxIterations`, `untilFinishReason`, `combineStrategies` |
| Interrupts | `validateInterruptResumeBatch`, `withInterruptBinding`, `addToolApprovalResponse` |
| Run takeover | `defineRunStore`, `DetachableRunCapability`, `requestRunCancel`, `locks` export |
| Other activities | `summarize`, `generateImage`, `generateAudio`, `generateVideo`, `generateSpeech`, `generateTranscription` + their `use*` hooks |
| Realtime | `realtimeToken`, `useRealtimeChat` |
| MCP | `ChatMCPOptions`, `useMcpAppBridge`, `createMcpAppBridge` |
| Message conversion | `convertMessagesToModelMessages`, `modelMessagesToUIMessages`, `uiMessagesToWire` |

The `chat_interrupts` table exists here with nothing writing to it, because the
store contracts come as a set and half of one is worse than none.

## Transferable lessons

- **A large library has a small load-bearing core.** Twelve symbols carried this
  entire POC. Find the core before reading the index.
- **The reference implementation is the specification.** `memoryStream`'s source
  answered questions the type docs didn't. Read it beside any backend you write.
- **Ids flow in, not out.** `chat()` takes `threadId`/`runId` rather than minting
  them, because resumability requires the *caller* to be able to name the run
  again later.
- **Type an adapter as the narrowest interface that works.** Returning
  `StreamDurability` instead of the inferred type is what keeps an optional
  capability from silently becoming a dependency.
- **When a library applies a rule it doesn't export, restate it exactly once.**
  Two readings of the same request that disagree is a bug class, not a bug.
